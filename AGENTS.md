## General rules

### Spec gate
No code changes without a governing, approved spec. If implementation needs to diverge from the spec, update the spec first, not after. Keep a change log. Require explicit go-ahead before starting implementation on a new or changed spec. A story's Tier 2 spec — extracted from its parent epic — is the first commit on that story's feature branch, not an artifact written alongside or after the code.

### Documentation status contract
Every doc declares an owner, a status, a last-updated date, and a review-by date. A doc must declare exactly one type (tutorial, how-to, reference, or explanation — Diátaxis framework) and not blend types within one file.

### Pre-share quality gate
Before sharing or committing spec/backlog artifacts: resolve all TBDs and placeholder tokens, confirm no secrets are staged, and stage only the files that were actually discussed/reviewed.

### Traceability
Reference the full issue key for whatever tracker the project uses — no shorthand. Design references (Figma etc.) must point to a specific frame or node, not a whole file. Confirm links resolve before including them in a spec or handoff doc.

### Knowledge governance — route, don't store
Maintain a single home for any given fact. Don't duplicate knowledge across docs; derive it from the source system automatically wherever possible instead of copy-pasting a snapshot that will go stale.

### Rule-parity via generation, not memory
`AGENTS.md` is the only rules file a human edits. Every other tool-specific file (`CLAUDE.md`, `.cursor/rules/*.mdc`, `.github/copilot-instructions.md`) is regenerated by the CLI. A pre-commit or CI check fails if a generated file doesn't match what regeneration would produce.

### Command-first instructions
Build, test, and lint instructions must be exact, copy-pasteable shell commands for this repo's real toolchain — not prose describing them. See **Build commands** below.

### Compliance is machine-checkable
Every rule should be phrased so a script could plausibly check it: spec exists and is approved before a diff opens; every doc has the four metadata fields; no TODO/TBD strings in staged spec files; generated rule files match their source; every status-transition timestamp is a datetime, not a bare date.

## Discipline — App / product engineering

These rules apply to this Next.js web application. They were established from C&T org audit findings across TypeScript/Next.js repos.

### Server-first rendering
React Server Components by default. A Client Component (`"use client"`) is an explicit, justified exception — note the reason in the component or its associated spec. Do not add `"use client"` just to unblock a hook; push state up or restructure.

### Server Actions
Mutations go through Next.js Server Actions (`"use server"` in `app/lib/actions.ts`). Validate all inputs at the action boundary using Zod before any database write. The `deleteInvoice` stub in `app/lib/actions.ts:121` is an intentional tutorial placeholder — do not implement without a governing spec.

### i18n
All user-facing strings must go through the i18n layer — none hardcoded directly in JSX. (Currently no i18n library is configured; if one is added, enforce this rule from the point of introduction.)

### Styling — design tokens only
Use Tailwind utility classes and the configured `cn()` helper (`lib/utils.ts`) for all styles. No ad-hoc hex values or magic numbers in component styles. Do not introduce inline `style={{}}` for anything covered by Tailwind.

### Authentication boundary
The auth middleware (`proxy.ts`) protects all non-static routes. Any new route under `/dashboard` is automatically protected. A route that intentionally bypasses this protection requires an explicit spec decision — not a comment in code.

### Debug routes
`app/query/route.ts` (`GET /query`) is a tutorial debug endpoint — not a production API. Do not extend it; remove it before any production deployment.

## Stack — TypeScript / Next.js (App Router)

### TypeScript
Strict mode is on (`tsconfig.json`). Do not use `any` to unblock a type error — use `unknown` and narrow, or open a spec question if the correct type isn't clear.

### App Router conventions
- Route segments live under `app/` only — no `pages/` directory.
- Route-specific UI (loading, error, not-found) uses the Next.js file conventions: `loading.tsx`, `error.tsx`, `not-found.tsx`.
- Shared UI components live under `app/ui/`. Shared library code (data, actions, types, utilities) lives under `app/lib/`.
- `lib/utils.ts` at the repo root is the Tailwind class-merge helper (`cn`) only — do not add other utilities there.

### Database access
Direct PostgreSQL via the `postgres` npm package. Connection is established with `POSTGRES_URL` from environment (SSL required — never disable). All queries are raw SQL via tagged template literals — no ORM. Query functions live in `app/lib/data.ts`; mutations live in `app/lib/actions.ts` only — never query the database directly from a UI component or a page.

### Dependency management
Package manager is **pnpm**. Do not use `npm install` or `yarn add`. Update `pnpm-lock.yaml` with every dependency change.

### Environment / secrets
Secrets (`POSTGRES_URL`, `AUTH_SECRET`, etc.) live in `.env` (gitignored). Never commit secrets or reference their values in a spec, rule file, or agent-visible context — reference them by environment variable name only. `.env.example` documents the required keys without values.
